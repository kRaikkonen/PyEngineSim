## 0. 一句话结论

现在其实有**四套各自演化的系统**：Python 声音（真理）、Swift 声音（手抄）、Python 车模式、Swift 车模式，
外加一条靠人肉的发布链。这几个月的问题（Swift 落后、延迟、转速不顺、低转不好听、音量被拉平、
每个 bug 都要夜里上车试、证书每周过期）不是某个函数写错，是**结构**造成的。

v2 的结构：

1. **发声链逐段重做，从单次点火开始（核心，§6）**：不再"画一个脉冲再加工"，而是把每个缸经排气门的放空实时解出来
   （带单位的质量流量），送进按排气拓扑建的波导网络，再辐射出去。循环变动、流噪声、陡峭化是模型的一部分。
   单个爆炸声用实录做事件级验证——你的 A3 是标定台。
2. **一个编译型核心（Rust），只写一次**：里面两半——`sound`（实时发声）和 `link`（OBD 对话 + 车辆状态估计）。
   iOS、桌面、以后的 Android 都用同一份。不再有"移植"和"对拍"。
3. **车载链路从"跟随 OBD 读数"改成"车辆状态估计器"**：融合 OBD 转速、车速、踏板/负荷和**手机加速度计**，
   在"声音真正出喇叭的那一刻"给出转速。每一段延迟都**测出来**再补偿。
4. **桌面可复现**：行程记录器 + 仿真 A3。上车一次录下来，之后在桌面上重放无数次；不再用你的夜晚当调试器。
5. **Python 退到它擅长的位置**：离线物理烘焙（可读可改）+ 桌面工作室 UI。运行时发声不再是 Python。
6. **两条线并行、渐进**：车载链路先修（几周内）；新发声链在核心里逐段建成，旧声音冻结并存，一台车过了你的耳朵才切换。
   任何时候都有一个能开的版本。

## 2. 现有设计缺陷（带证据）

证据来自 2026-11-12 对工作区做的两份独立代码审查（Python 端、Swift 端）和本项目的工作记录。
延迟数字是**按代码推算**的，不是实测（实测是 L0 的任务，§12）。

### A. 一个声音，两份实现，现在谁也不是真理

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| F1 | **声音核心写了两遍，而且已经对不上了** | Swift 是 Python 的手工移植，靠逐采样对拍维持：16 个生成脚本、约 50 MB 夹具。21 个夹具里 17 个停在 2026-08-30，此后 `audio.py` 从 4101 行长到 7341 行（33 次提交）。夹具用的预设/表/扭矩数据与随 app 发布的那份 **0/131 相同**。6 个夹具在仓库里没有生成脚本。反过来 Swift 也有 Python 没有的行为（`DriveModel`、`PedalPredictor`、`BLELink`、29 位 OBD） | "逐采样一致"只对一个旧的 Python 成立；每个功能做两次；Swift 永远落后（赛道边、物理声源、气门进气、闭环 EGT 至今只有 Python 有） |
| F2 | **验证的不是发布的** | 所有对拍测试跑在块长 256，app 跑 512。AGC/限幅/抖动的时间常数是"按块"写的，app 里全部慢一半；混响延迟下限是 `block+1`（`Reverb.swift:72-77`），512 时进气腔混响和座舱混响的梳状滤波器全部塌成同一个 513 样本。app 从不设置 `pov`，座舱分支不可达——**车里放的其实是车外追拍视角** | 你听到的不是测试保证的那个声音 |
| F3 | **为了对拍，必须复制"输出依赖调用历史"的怪癖** | 滤波器缓存按 `int(fc/8)` 分桶、谁先调用用谁的精确频率、超 800 条整体清空（`audio.py:2565-2588`；Swift 照抄：`BangFizz.swift:18-54`，注释原话"复现声音就是复现缓存"）；38 处噪声抽取共用一个 RNG，加一层噪声后面所有 stage 全变；`_turbo_flow` 每 25 rpm 记住第一次见到的转速（`simulator.py:260-266`）；消声器读上一块限幅后的输出电平（`audio.py:3808`） | 同样的输入，先跑过什么决定了输出；导出参考数据时要专门关掉记忆才能复现 |
| F4 | **Python 那份达不到自己的实时预算** | 44.1 kHz/块 256（预算 5.8 ms）单核占用：RS3 0.61、Aventador 0.71、Veyron 0.99，赛道边视角 0.86–1.22；最坏单块 18.7 ms。测试用的带种子路径更慢（1.25–1.72），**被测路径不是发布路径**。加上 GIL（物理 + 绘制 + 合成抢一个核），手机上只能 24 kHz/512 | 桌面爆音是结构性的；"真理"实现上不了手机 |

### B. 实时与线程

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| F5 | **Python：物理跑在界面的时钟上，音频不加锁地读** | `sim.step()` 只有一个调用点（`app.py:1604`），由 60 fps 的界面循环驱动。音频每块读一次 `sim.omega`（`audio.py:2794`）并保持，之后同一块里又读 36 次 `sim.rpm`、16 次 `sim.throttle`，没有快照。`audio.py:1814` 创建的锁**从未被获取**。音频线程反过来写物理对象（`ts.air.bov_mode`、多个缓存）。涡轮因此存在两份（帧率的机器 + 音频率的 `Twin`） | 转速以 60 Hz 台阶到达音频；画面一卡，物理轨迹就变 |
| F6 | **模拟器没有"被外部驱动"的模式** | 燃烧倍率 `_k_burn` 只在 `step()` 里求解（`simulator.py:1114`），构造时是占位值 3.0；`last_blowdown` 只在 `_compute_torque` 里写。车模式（`carmode.py:159-197`）、Forza 模式、`golden.py` 都直接设转速油门、从不求解。导出脚本各自手工打补丁并自己写明（`make_swift_physics_fixture.py:59-66`）。Swift 同病：`physics.lastBlowdown` 初始化后从不更新 | **车模式和 golden 参考用的是发动机从不运行的脉冲强度**；每个调用方重新实现 `step()` 的一个子集 |
| F7 | **Swift 渲染路径不是实时安全的** | 约 80 处每块数组分配（核心共 94 处 `[Double](repeating:)`），静态估算每 16 ms 约 300–400 次堆分配（≈2 万次/秒）；37 处 `p("…")` 字符串键查参数，其中 3 处在逐采样循环里（每块约 1500 次字符串哈希）；32 处把系数数组转成字符串来判断是否重调；混响用 `removeFirst`；波导每次调用拷进拷出 2600 样本；渲染线程是普通优先级 | 平均 CPU 没问题，**抖动**有问题——这正是需要 96 ms 队列的原因 |
| F8 | **三个线程共享可变状态，零同步** | 整个核心只有 4 把锁（都在蓝牙缓冲和日志上），没有原子量。OBD 线程逐个写 `rawRPM/dRPM/时间戳/踏板/车速/挡位`，主线程成组读（会撕裂）；主线程写 `physics.rpm/throttle/boost`、`params` 字典、图层集合，渲染线程读；换车时主线程替换 synth 而渲染线程正在用它；`stop()` 不等轮询线程退出，旧线程可能对新连接说话 | 未定义行为；偶发的单帧转速毛刺 |
| F9 | **控制回路挂在界面定时器上** | 50 Hz `Timer` 在主线程（`AppModel.swift:251-255`，滚动界面时会暂停）；每 20 ms 改写约 12 个 `@Published`，触发 841 行的 `ContentView` 重算；转速每块（16 ms）才生效一次，50 Hz 对 62.5 Hz 不同步；demo 模式完全没有平滑 | 无论估计器多好，音高都是台阶状的、带抖动的 |

### C. 车载链路

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| F10 | **延迟预算从未测量；路由延迟没人读** | `AVAudioSession.outputLatency`（音频**路由**的延迟，车机蓝牙 A2DP 约 150–300 ms）在整个 `swift/` 里 **0 次引用**。按代码算，`set(rpm)` 到出声 75–135 ms（不含路由）；外推却只按"队列 + 硬件缓冲"补。所有时间戳都是墙上时钟，没有单调时钟或音频时钟 | 补偿的是猜的数；如果走车机蓝牙，最大的一段延迟完全没被处理 |
| F11 | **转速"估计器"是对一个带噪导数的线性外推** | 相邻读数差分 → 0.35 平滑 → 外推最多 0.45 s（`OBDTelemetry.swift:147-158`）；每个新读数让基准跳一下。**外推后的值再过转速映射**：`low-rev lift` 拉满时怠速附近斜率约 4 倍，叠在 ratio/stretch 的斜率上，低转的抖动被放大约 6 倍。`ShiftDetector` 用界面的 20 ms 步长去除一个每 100 ms 才变一次的转速（`OBD.swift:335`），−3000 rpm/s 的门限实际只有约 −600 rpm/s → 误判换挡、误切油门。没有离群值检查（一个坏读数会被播出来，还会永久抬高学到的红线）；没有过期保护（链路卡住时外推值最多保持约 8 秒） | "不流畅"的直接来源；ratio + lift 时最明显 |
| F12 | **没有车辆模型，没用手机传感器** | 在挡时 `转速 = k挡 × 车速` 这条关系没用；`CoreMotion`/`CLLocation` 0 次引用。demo 模式里其实有一个车辆模型（`DriveModel.swift`），实车模式没用它 | 延迟和抖动是"只跟随 OBD 读数"的固有属性，调参数调不掉（§7.5 的仿真） |
| F13 | **协议层靠试错，而且零测试** | `probeCar` 是 21 级梯子，级与级之间依赖上一级残留的适配器状态；不保存成功路径，每次重连重走 25–30 个来回。**没有任何测试实例化过 `OBDTelemetry`、`BLELink`、`AudioOutput`、`AppModel`**；假 dongle（`fake_elm327.py`）只会 11 位标准车。Python 车模式更落后（默认 11 位、无踏板预测、无 BLE） | 所有抱怨背后的那部分代码，恰好是唯一没有参考、没有仿真、没有回归测试的部分——A3 只应答 29 位这件事花了 10 天、多轮夜间上车 |

### D. 声音结构

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| F14 | **合成器是一个 2241 行的函数** | `_render_block`（`audio.py:2792-5032`）：214 个分支、约 362 个局部变量、842 个浮点字面量。类上 362 个属性，其中 145 个在热路径里用到时才创建（116 处 `getattr(self, …)`）；stage 之间靠旁路属性通信（`_comb_load`、`_valve`、`_bov_env`…） | 没有哪个 stage 能单独测试、替换或移植；Swift 移植时得自己发明 stage 边界，端到端测试才抓出 7 个接线错误 |
| F15 | **一切按块，时间常数用"块数"计** | AGC、限幅、压缩的平滑系数是每块常数；增益按块阶跃；管长延迟按块取整；滤波器每块重新设计（Python 每块 90 次 `lfilter`、72 次 `np.zeros`）。块长：桌面 5.8 ms、golden 8 ms、手机 16–21 ms | 行为随块长和采样率改变（F2）；转速变化时的"台阶感"是内建的 |
| F16 | **响度是一个反馈归一化器加一堆补丁** | AGC 把一切拉回 RMS 0.22，代码里明说"绝对响度交给下游 AGC"（`audio.py:1640`）——实测全油门高转比怠速还**小** 1.5 dB（A3）/ 4.5 dB（Aventador）。围着它的补丁：点火增益上限、涡轮层除掉上一块的增益、`sustain_on_lift`（注释原话"可能是谎言"）、赛道边另算、录音师上限、`_PHYS_MAKEUP = 100`、`real vol`。四级串联：AGC → F1 压缩器 → 峰值限幅 → tanh。层电平是相对别的层的耳调常数（33 个 `_TB_*` 等） | 没有哪一层有一个说得出的电平；每加一个声源都要再给 AGC 加一条例外 |
| F17 | **同一个物理量几套模型并存；出错时静默换模型** | 缸压有 4 套（扭矩用的 Wiebe、音频用的闭式、`gas_truth`、没人调用的 `gas_moc`）。经典/物理声音被 50 多处分支交织，而**没有任何预设打开物理声音**。57 处 `_HAVE_SCIPY` 判断全是死分支（已硬编码为 True）。43 处 `except Exception`，最糟的几处会静默换掉 VE 模型、涡轮、脉冲模型，或吞掉渲染异常——记录在案的代价：一次 60 K 的进气温度误差，表现为 41 音分的音高偏差，两轮没发现 | 每个改动做两三遍；坏了的车照样出声，回归靠耳朵几周后才发现 |
| F18 | **声音是按"全油门 + 对着录音"调的** | 所有验证录音都是全油门车载或飞越；1000–2500 rpm 小油门从未作为验收工况 | 车里 95% 的时间恰好落在没验证过的区域 → "低转不好听" → `low-rev lift` 补丁 |

**值得保留的**（v2 不重写，只搬家）：

- 白盒物理模块 `ve_model`/`map_model`/`bmep_model`/`turbo.py`/`gas_truth.py`/`exhaust_tmm.py`——只依赖 `math`/numpy，天然适合离线烘焙。
- "离线烘焙 → 运行时查表"的模式（`surrogate.LUT`、`engine_tables`）：这是两种语言之间正确的边界。
- 事实检查（`run_fact_checks`）、134 台车的事实数据、check set 纪律。

## 3. 设计原则

1. **一个核心，一次实现。** 发声和车载逻辑只存在于一处；所有平台链接同一份。
2. **离线算贵的，运行时只做必须实时的。**（沿用 PLAN §5.1.3）物理扫频、涡轮选型、气体真值在 Python 里离线跑，产物是数据。
3. **实时安全是规则，不是希望。** 渲染线程：不分配、不加锁、不做系统调用；用测试强制（§10）。
4. **输出是输入的函数。** 不允许依赖调用历史的缓存、共享 RNG、懒创建状态。
5. **先测量，再补偿。** 每一段延迟都有一个读得到的数；补偿量 = 测得的数。
6. **估计，而不是跟随。** 车的状态由一个带物理模型的估计器给出，传感器只是修正它。
7. **凡是上车才能发现的，先让它在桌面上能复现。** 记录、回放、仿真车是一等公民，不是事后工具。
8. **物理量纲贯穿。** 声源输出 Pa / m³·s⁻¹；响度只在最后一级、按一条明确的曲线映射。
9. **数据驱动差异。** 车与车、协议与协议的不同放在数据（car pack / vehicle profile），不放在代码分支。
10. **每阶段独立可验收、可回退；任何时候有一个能开的版本。**

## 5. 核心：语言与实时规则

### 5.1 语言

这台 Windows 没有任何编译器，所以无论选什么都要装一套工具链；选择标准是**我能在这台机器上、不靠 Mac、
秒级地编译和跑全部测试**，以及产物能进 iOS/Android/Python。

| | Rust（**推荐**） | C++17 | 维持现状（Python + Swift 双实现） |
|---|---|---|---|
| Windows 上开发 | `rustup`，免管理员，自带链接器 | 需装 llvm-mingw 或 VS Build Tools | Swift 只能在 Mac 上验证（F21） |
| iOS / Android | 静态库 + C 头文件；Mac 上一次性装 rustup | Xcode/NDK 原生支持，零额外工具 | 现状 |
| Python 调用 | cffi（本机已装 2.0.0） | cffi | — |
| 线程共享状态的数据竞争（F8） | **编译不过** | 靠自觉 + sanitizer | 现在就有 |
| 越界/悬垂 | 编译期或立即 panic（测试里必现） | 静默内存破坏 | — |
| 跨平台逐位一致 | 默认不融合乘加；`exp`/`ln`/`sin`/`cos` 是核心里自己写的纯算术（`sound/src/math.rs`，不调用平台数学库，也不依赖外部 crate）→ **Windows 上的 golden = 手机上的输出** | 需手动 `-ffp-contract=off` + 自带数学库 | 靠对拍 |
| 复用 C++ 原版 engine-sim 的气体求解器 | 可经 C ABI 链接（离线用） | 直接 | 现在是 Python 移植版 |
| 代价 | 新发声链和链路直接写在核心里（旧链不移植，§6.9）；Mac 上多一个工具 | 同左 | 0，但 F1–F9 留着 |

推荐 Rust 的核心理由：这份代码由我维护、几乎没有人工 code review，能跑的地方只有测试和你的车。
**把一整类错误（数据竞争、内存破坏）从"上车才发现"变成"编译不过"，价值最大。**
你如果偏好 C++（和原版 engine-sim 同语言），方案其余部分不变。

### 5.2 `sound` 的实时规则

- 渲染函数里：**零堆分配、零锁、零系统调用**。所有缓冲在 `open` 时按最大块长分配。测试里用计数分配器断言"渲染 10 万块，分配次数 = 0"。
- **内部控制块 32 样本**（48 kHz 下 0.67 ms）。控制量（转速、负荷、增压、各滤波器的截止频率）每个控制块线性过渡，不再每 8–16 ms 跳一次（F15）。
- 滤波器换成**对调制稳定**的拓扑（TPT/状态变量），系数由当前参数直接算——不再有"按 8 Hz 分桶、谁先来用谁的"缓存（F3）。
- **每个噪声源自己的 RNG 流**（按 stage 名 + 种子派生），不再共用一个（F3）。
- 输入是一个**无锁控制快照**（三缓冲/seqlock）：`{转速, 负荷, 增压, 事件, 时间戳(采样时钟)}`。壳和 `link` 写，渲染线程读。
- **原生 48 kHz、立体声**接口。（现在 32 kHz 渲染后线性插值到 48 kHz，高频有镜像损失；单声道。）立体声内容按 PLAN L6 逐步填。
- **时间常数一律以秒表示**，延迟以秒/米表示；行为与块长、采样率无关（F2、F15）。测试在 64/256/512/1024 四种设备块长下断言输出一致。
- **引擎状态是工况的纯函数**：核心收到 `{转速, 负荷/进气压力, 温度}`，自己推出燃烧倍率、脉冲强度、逐缸状态。自由运行、车载、测试、烘焙走同一条路——不再有"只在 `step()` 里才求解"的量（F6）。
- 出错即失败：烘焙期任何模型失败直接报错、不出 pack；运行时每个量只有一个模型，没有静默回退（F17）。
- 确定性：同一 pack + 同一控制序列 → 逐位相同的输出，任何平台。
- 性能目标：iPhone XS（A12）上 ≤ 10% 单核（现在 Swift 约 30%，Python 150%）。
  **S1 实测**（这台 Windows 的一个核，`cargo run --release --example bench`）：A3 四个缸的气缸模型占 2.2–3.3%；16 缸赛车缸盖占 19%，还要再压（见 §6.2 末）。
  **S2 实测**：A3 整条链（四个缸 + 15 段管的排气网络 + 气流噪声 + 响度曲线）占 5.0–7.2%。

>
> 所以 v2 的发声链**不是**把现有 24 个 stage 换一种语言重写，而是重新建模。物理内容以
> `ENGINESIM_PLAN.md` 的 L0–L8 为纲；这里写清楚每一段从什么换成什么、怎么验证。

### 6.1 现在的"单个爆炸声"是什么

三步配方（Swift 的 `PulseTrain` / `BangFizz` / `SourceStage`，与 `audio.py` 对应）：

1. **画一个脉冲**：`blow = (0.7 + load) · hard(d / rise) · exp(−d / τ_blow)`，再加一个余弦起始的缓峰 `disp`。
   **所有量都以曲轴角度计**（`rise` 2–6°，`τ_blow` ≥ 2.5°）；气门窗口固定在 505°–715°；
   每个缸的"个性"是随车导出的随机散布（幅度、衰减、边沿）。
2. **拆成 bang 和 fizz**：bang = 0.55 × 脉冲（低转时再过一个 18–70 Hz 高通）；fizz = 脉冲 × 白噪声 + 一个常数底噪。
3. **加工成"燃烧事件"**：气道混响器、正负不对称、三个早期反射抽头、"crack"（脉冲的微分）、
   "body"（一组高 Q 谐振器被那个微分沿激励，音高跟点火频率走，谐波比例是一张固定的表，另有 5 套音乐和弦可选）、tanh 饱和。

物理上的问题：

- **时间结构的类型就不对。** 泄压是"气缸经排气门放空"：它的快慢由 `τ ≈ V / (A·c)` 决定，是**时间**量；
  只有气门升程是曲轴角量。把整个形状钉在曲轴角上，脉冲就随转速等比例变窄、变亮。
  下表右两列是现有脉冲公式；左列是 v2 核心里的气缸模型算出来的（`cargo run --release --example event`，
  A3 一个缸，增压 1.8 bar 全负荷；气门升程用了接近量产凸轮的型线，见 §6.2 末"S1 的发现"）：

  | 全负荷 | v2 核心：上升 / 宽度 | 现在：上升 / 宽度 |
  |---|---|---|
  | 1500 rpm | 2.3 ms / 4.7 ms | 0.17 ms / 0.64 ms |
  | 2500 rpm | 1.7 ms / 3.7 ms | 0.10 ms / 0.38 ms |
  | 6000 rpm | 1.0 ms / 2.8 ms | 0.05 ms / 0.16 ms |

  物理上脉冲宽度从 1500 到 6000 rpm 只缩到 0.6 倍；现在的缩了四倍，且整体短一个量级。后面的滤波器和混响是在给这个源头补救。
- **负荷只改幅度，不改性质。** 同一个模型、同一台 A3，只改进气压力（单缸排气门流量）：

  | 1500 rpm | 开阀时缸压 | 流量峰值 | 宽度 | 开阀后前 1/4 段排出的份额 |
  |---|---|---|---|---|
  | 进气 0.30 bar（怠速/滑行） | 1.7 bar | 9 g/s | 13.8 ms | 0% |
  | 进气 0.50 bar（巡航） | 2.8 bar | 27 g/s | 3.0 ms | 42% |
  | 进气 1.00 bar | 5.8 bar | 60 g/s | 4.3 ms | 67% |
  | 进气 1.80 bar（增压全负荷） | 10.9 bar | 110 g/s | 4.7 ms | 72% |

  小油门时开阀那一刻缸压只比排气口高一点，没有壅塞的泄压冲击，气体是被活塞在整个排气行程里推出去的——
  一个十几毫秒的软脉冲；进气压力到 0.5 bar 以上才出现真正的泄压峰。流量峰值从怠速到增压全负荷差 12 倍（22 dB）。
  现在的模型里它们是**同一个形状**乘以 0.9 或 1.7。日常工况（小油门）恰好是模型最不像的地方（F18）。
- **"身体"和"脆响"是后加的配方**，不是从事件里长出来的：body 是被激励的谐振器组，crack 是微分器，
  fizz 是白噪声，各有各的耳调电平，彼此没有物理关系。
- **逐缸差异是随机数**，不是歧管长度和汇合位置；V 型机的排气律动靠 14°/18°/9° 的假相位偏移。
- 以前两次想换掉它（Tier B 的"求解器脉冲"、物理声源）都输给了耳朵，原因有记录：脉冲被峰值归一化并去掉直流，
  "身体"丢了；只用一个代表气缸、假设均匀点火；没有循环变动和流噪声，所以"太丝滑、像吸尘器"；
  电平比经典低 40 dB，靠 `_PHYS_MAKEUP = 100` 硬拉。**不是物理路线错，是它被 Python 的算力和旧链的包袱逼成了残缺版。**

### 6.2 v2 的单次点火：把每个缸的放空实时解出来

有了编译型核心，就不需要"画脉冲"，也不需要"烘焙脉冲表"。每个缸、每个采样解一步：

```
缸内状态 (m, T)，体积 V(θ) 随活塞运动

排气门质量流量   ṁ = Cd · A_v(θ) · p_cyl / √(R·T_cyl) · Ψ(p_port / p_cyl)
                 Ψ：可压缩孔口流量函数；p_port / p_cyl < 0.546 时壅塞（声速喷流）
气门流通面积     A_v(θ) = 凸轮升程曲线 × 气门帘面积      ← 曲轴角量；可变气门直接改这条线
缸内             绝热放空 + 活塞做功
起点             排气门开启时的 (p, T, m)：来自循环模型（进气压力、充气效率、空燃比、燃烧）
                 ——用已有的烘焙表，扭矩和功率的数值不受影响
气门外的压力     p_port：排气网络在气门处的瞬时值（反射波回来会真的改变放空）
```

得到的是**带单位的质量流量（kg/s）**。一个事件里自然包含：

- **泄压段**——硬还是软由开启时的缸压决定（负荷越大越硬，这是物理，不是参数）；
- **排挤段**——低频、与活塞速度同形，就是"身体"的来源；
- **气门重叠的回流**——高转凸轮怠速时的"喘"从这里来。

转速、负荷、断缸、限转、背压、增压、可变气门、停缸——都只是改输入，不是另写一段代码。
同一套模型用于进气门（进气声）。

**S1 已实现**（`core/sound`，2026-11-12）：上面这套方程已经在核心里，每个采样、每个缸解一步：

- 单区缸内气体（比热比随温度变化），活塞做功、Wiebe 燃烧、Hohenberg 壁面传热，进排气门都用可压缩孔口流量。
- **气门这一步是隐式解的。** 上止点附近气缸只有几十毫升、两个气门同时开着，它和气道的平衡比一个采样还快；
  显式算法在这里会振荡（赛车缸盖上直接发散）。隐式解对任何缸盖、任何转速都稳定，A3 上平均每个开阀采样只需 1.2–1.8 次求值。
- 气道不只是一个压力：它可以是一根管（`p = p_in + z·q`，气门推进去的流量自己把气道压力顶高）。
  阀和管是联立解的——S2 的排气网络就接在这个接口上，不用改气缸。
- 流量函数是等熵喷管公式的多项式拟合（误差 3e-9，脚本生成、测试对照原公式），最内层没有幂函数。
- 成本（这台 Windows 的一个核）：每缸每采样 130–180 ns，A3 四缸占 2.2–3.3%。目标是再降一半；16 缸现在 19%，偏高。

**S1 的发现**（都影响"单个爆炸声"长什么样）：

1. **凸轮型线比想的重要。** `gas_truth.py` 合成的气门升程是 cos⁴ 形：半升程持续角只有总持续角的 36%，
   开阀后前 40° 几乎没开。量产凸轮是 55–62%。换成接近量产的型线后，全负荷下开阀后前 1/4 段排出的气体从 21% 变成 68%——
   泄压早得多、硬得多。预设里没有凸轮数据；**真实的气门升程曲线是 car pack 必须带的事实**（§9），A3 的要查证。
2. **`gas_truth.py` 的充气量不能直接用。** 它让进气道气体的"冲击压力"最高到静压的 1.58 倍，算出的充气效率是 1.15–1.39；
   同样的气门，核心自己吸气得到 0.85–0.93（真实自然吸气发动机约 0.85–1.05）。运行时本来也没用它的原始充气量（`ve_max` 是另解的），
   所以核心的充气量取自现有的烘焙表，而不是 `gas_truth`。

| 逐缸差异 | 随机"个性" + 假相位偏移 | 每缸自己的歧管长度、汇合位置（几何）；左右排各自的出口 | 阶次谱对录音（PLAN §5.3 的容差） |
| 循环变动 | 幅度抖动约 ±6%，高转加大 | 燃烧的循环变动：全油门约 1–3%，怠速/小负荷 5–15%，作用在**开启时的缸压**上——幅度、形状、时刻一起变 | 录音里逐循环幅度的统计 |
| 气流噪声 | 白噪声 × 脉冲 + 常数底噪 | 气门座喷流、管内湍流、尾管射流：功率按**当地瞬时流速**的标度律，带限；包络天然跟着流量走 | 谐噪比随负荷的变化对录音 |
| 气道、歧管、汇合 | 混响器 + 3 个固定抽头 + 两个梳状"波导"，靠 res1/res2 两个旋钮混合 | 一维线性波导**网络**，由排气拓扑图编译：每段管的长度、管径、温度 → 延迟与损耗；汇合、变径处按面积比散射 | 传递函数对 `exhaust_tmm`；阶次 |
| 大振幅 | `sig += k·sig·\|sig\|` 和 tanh | 行波陡峭化：传播速度 `c + (γ+1)/2·u`（与振幅相关的延迟），按每段管里的实际振幅 | 高负荷时谐波的增长对录音 |
| 涡轮 | 低通 + 废气门混合 | 网络里的一个二端口（收缩 + 损失），流通能力取自已有的涡轮机器 | 涡轮前后的频谱差 |
| 催化、GPF、消声器、阀门 | 低通、峰值滤波、谐振腔、腔体延迟、"de-honk"、"thunder"、电平触发的"blow-out" | 全部是网络元件：多孔段（流阻）、膨胀腔（变径波导段）、旁支谐振腔、穿孔/吸声段、阀门（可变面积的支路） | 传输损失曲线对文献公式 |
| 尾管出口 | 辐射混合旋钮、金属环、megaphone | 开口端反射（Levine–Schwinger）+ 单极子辐射（声压 ∝ 体积流量的时间导数）+ 射流噪声 + 指向性；管壁辐射按材料 | 管内与远场的电平差 |
| 进气 | 噪声带 + 正弦堆（Swift）；气门流烘焙（仅 Python） | 进气门同一套放空模型 → 进气网络 → 进气口辐射 | 进气/排气电平比（实车低 10–25 dB） |
| 机体与机械声 | "锅盖"低通 | 缸压上升率的频谱 × 机体衰减 → 辐射；配气、喷油、齿轮是冲击/啮合源 | 怠速近场录音 |
| 听者 | 车外追拍视角（车里也是，F2） | 座舱：隔声透射 + 结构传声 + 腔模态；车外视角只进工作室 | 车内录音 |
| 响度 | AGC + 补丁 | §6.6 | — |

**S2 已实现**（`core/sound/src/network.rs`，2026-11-13）：排气是一张由"管段 + 节点"组成的网络，接在 §6.2 的气道接口上。

- **管段**：两个方向的行波各一条延迟线（分数延迟，立方插值），长度、截面、温度决定延迟和阻抗；
  管壁损耗只作用在声音上，对稳定流量增益恰好为 1。
- **节点只有四种**：汇合（任意根管，同一压力；只有一根就是封闭端）、气门（某个缸往里排）、
  节流（压降 = r·q + k·q|q|：涡轮、催化器载体、阀门；可由工况实时调节，VTG 叶片开度就是这样进来的）、
  开口（尾管出口：无法兰管口的反射 + 单极子辐射）。
  消声器、谐振腔、催化器都**不是**单独的元件：膨胀腔是一段粗管，旁支谐振腔是一段一端封闭的管，
  催化器是一段粗而有损耗的短管后面跟一个线性流阻。
- **质量严格守恒**：气门推进去多少，尾管出来多少（测试：差 1e-9）。涡轮前的背压因此是算出来的，不是给定的。
- **气流噪声不是事后加的一层**：凡是气流损失压力的地方（气门座、节流、尾管出口），那份损失本身带湍流脉动，
  频带由当地流速 / 当地尺寸决定。所以嘶声只在气体高速流动的那几毫秒出现，随流速的三次方增长，
  并且被它下游的管路滤过。
- **循环变动**（§6.4 的第 1 条）也已在气缸里：每个循环的着火时刻、燃烧速度、完全程度各不相同（`Control::ccv`）。
- **响度曲线**（§6.6）在输出级：按人耳加权的电平定增益，`dynamics` 一个旋钮；限幅器只做保护。

对公式的验证（`cargo test --release --test network`，8 个测试）：

| 检查 | 结果 |
|---|---|
| 一端封闭一端开口的管，前三个四分之一波长共振 | 与公式（含管口修正 0.6133a）差 −0.6% |
| 膨胀腔（面积比 9）的传递损失，8 个频率 | 与教科书公式差 ≤ 0.4 dB |
| 节流的稳态压降 | 与 r·q + k·q² 一致到 0.1% 以内 |
| 一阵气流进去之后 | 出口流出的 + 管里存的 = 进去的（1e-9） |
| 整台 A3（怠速 / 巡航 / 全负荷） | 气门流量 = 尾管流量；任意块长逐位相同；零内存分配 |

A3 整条排气的数字（`_claude_scratch/v2pc/look.py`、`along.py`；管路尺寸是这类布局的典型值，**不是实测**）：

| 工况 | 排气流量 | 涡轮前平均背压 | 尾管后 1 m 声压级 |
|---|---|---|---|
| 怠速 800 rpm | 2.4 g/s | 3 mbar | 54 dB(A) |
| 巡航 2000 rpm，进气 0.55 bar | 13 g/s | 28 mbar | 70 dB(A) |
| 全负荷 3000 rpm，1.9 bar | 73 g/s | 0.41 bar | 72 dB(A) |
| 全负荷 5000 rpm，1.9 bar | 123 g/s | 0.88 bar | 72 dB(A) |

**S2 的发现**：

1. **没有气流噪声，尾管出来的只是一个"嗡"。** 纯管路模型里 A3 尾管处 500 Hz 以上比点火频率低 40–60 dB——
   涡轮、催化器、颗粒捕集器、消声器把脉冲的高频几乎全吃掉了。真实排气里那部分声音是下游的气流自己造的。
   所以气流噪声是模型必需的一部分，不是装饰。
2. **涡轮是最大的一道消声器。** 全负荷 5000 rpm 时歧管里点火阶次的压力脉动是 184 dB（约 0.45 bar 有效值），
   过涡轮后掉到 154–166 dB。原因是节流的平方律：流量越大，它对脉动越"硬"。增压车安静是这个道理。
3. **响度必须按人耳算。** 怠速的四缸机大部分声压在 30 Hz 附近（听不见）；直接用声压有效值，怠速会被判成比巡航还响。
4. **A3 的消声器结构是猜的，而且很要紧。** 第一版用了两个理想的 8 升腔串联：5000 rpm 时点火阶次被压低 30 dB、
   它的二倍频 55 dB，尾管只剩嘶声。现在是一个带吸声的 10 升腔，阶次略高于嘶声。真车是哪一种，只有录音能定（S0）。
5. **气流噪声的量现在是起始值，偏保守**（各处损失脉动 0.6–0.8%）。文献里分离流是 5–10%，但按那个量全负荷就是"吸尘器"。
   这也要靠尾管录音定。

**还没有的**（S3）：管内大振幅波的陡峭化（高负荷的"撕裂感"、赛车排气的硬度主要来自它）、进气侧、机体与机械声、
涡轮自身的声音、座舱。**现在的听者站在尾管后 1 米。**

### 6.4 "颗粒感"从哪来（防止再变成"吸尘器"）

物理声源以前被判"太丝滑"，因为确定性的脉冲串本来就是丝滑的。真实发动机的粗粝来自三样东西，v2 把它们作为**事件的一部分**建模，而不是事后撒噪声：

1. **循环变动**：同一个缸每次燃烧都不一样。作用在排气门开启时的缸压上，所以每个事件的大小、软硬、到达时刻都略有不同；怠速和小负荷时最大——这就是怠速"突突"不均匀的来源。
2. **流噪声**：喷流和湍流的宽带噪声，强度由当地瞬时流速决定，所以只在气体真的在高速流动的那几毫秒里出现，并随负荷大幅增长。
3. **陡峭化**：大振幅的波在管里越走越陡，高负荷时高次谐波变多——"撕裂感"。

三者各自的量级都有文献范围和可测的对照量（上表"怎么验证"一列）。

### 6.5 单位贯穿

每个声源输出有量纲：排气口/进气口是体积流量（m³/s）→ 单极子 → 1 m 处声压（Pa）；机体、变速箱是 1 m 处声压。
层与层的电平关系由物理给出，不再是"相对涡轮层 ×0.36"这样的常数（F16）。物理声源以前"比经典低 40 dB"的问题不再存在——没有第二套标度需要对齐。

### 6.6 响度：一条曲线，取代 AGC

取消"把一切拉回 0.22"的 AGC。末级是：

```
播放电平(dB) = 基准 + D × (物理声压级 − 标定工况声压级)，再过限幅器（只做保护）
```

- **D（动态范围）是唯一的旋钮**：0 = 恒定音量（现在的行为），1 = 真实比例（怠速比全油门高转小约 40 dB）。车里默认值由你定。
- 物理声压级直接来自 §6.5 的量纲链，不是事后用 `30·log rpm + 20·log MAP` 估（`real vol` 现在的做法）。
- 车里另有一条**车速遮蔽补偿**：路噪随车速升高，同样的声音会被盖住；增益随车速缓升（原厂主动声浪的做法）。
- 涡轮层、松油门、赛道边不再各自和增益打架——因为不存在一个会动的全局增益了。

### 6.7 日常工况是第一验收工况

- 每台 check set 车加一段**巡航参考**（1500–2500 rpm、部分负荷）；验收指标同 PLAN §5.3（主阶次 ±3 dB、频带份额 ±6 pp），但在这个工况上算。
- §6.2 的事件模型在小负荷下给出的本来就是另一种声音（软、宽、排挤段为主）；`low-rev lift` 之类的转速映射只是 §7.6 里的选项，不再是掩盖手段。
- **小喇叭可听性**：手机和车门喇叭重放不了 60 Hz 以下，低转时基频常落在那里；用谐波结构（缺失基频）保证低转仍有"身体"。

### 6.8 验证：单个爆炸声要有"地面真值"

- **同步平均。** 低转时逐次点火在录音里是分开的。以转速为基准把上百个循环对齐、平均，得到"麦克风处的单个爆炸声"：
  平均波形、频谱、衰减，以及逐循环的方差（就是循环变动）。模型的事件必须在同一位置对上它。
- **你的 A3 就是标定台。** 它是唯一一台我们同时有"声音"和"真值工况"的发动机：行程记录器给出每一刻的转速、进气压力、负荷，
  手机麦克风同时录音。原地怠速、1500 / 2000 / 2500 rpm 定转速、轻踩几脚；麦克风分别放在尾管后和车内。
  先把 `a3` 这个预设（EA211 1.5T）做到与实录对上，方法成立了再推广。（需要给 app 加一个"只录不放"的标定模式。）
- **对独立的参考解**（`tools/core_check.py`，已通过）。同一组方程在 Python 里另写一遍，写成常微分方程、用 384 kHz 的龙格-库塔积分，
  与核心没有共用代码。核心在 48 / 96 / 192 kHz 下对它的误差按步长成比例减小（2000 rpm 全负荷：缸压 0.7% → 0.34% → 0.17%，
  排气流量均方根 0.15% → 0.04%；三个工况在 48 kHz 下缸压误差都不超过 1.4%，每循环排出质量差不超过 1.2e-4）——说明核心算的确实是它声称的方程。
- **对离线求解器 `gas_truth.py`**（同一个脚本，已通过）。我原先写"同一组方程，应当一致到数值误差"，**这句话是错的**：
  `gas_truth` 是原版 engine-sim 的气体模型，放空时带走的是内能而不是焓（缸内剩余气体不降温）、比热比固定 1.4、
  壁面传热系数是常数、排气歧管是集总容积。两者是不同的模型，只能交叉验证：给核心同样的气门、同样的充气量和燃烧，
  四个工况下开阀缸压差 11–17%，流量峰值差 13–17%，峰值位置差不到 2° 曲轴角，前 1/4 段份额差 0.02 以内。
- **其它车。** 沿用"只取派生特征"的录音规则（阶次表、频带份额），加上能找到的怠速/低转片段做事件级比较。

### 6.9 与旧声音并存

- 旧链（Swift 的 24 个 stage、Python 的 `audio.py`）**冻结**：不再加功能，也不迁入新核心。既然要重做，就不为将被替换的东西花几周做"逐采样等价移植"。
- 每台车一个开关：旧声音 / v2 声音；工作室里可以直接 A/B。**一台车的 v2 声音过了你的耳朵，才成为它的默认。** check set 先行。
- check set 全部通过后，旧链删除。某台车 v2 始终不如旧声音，它就继续用旧声音，直到找到原因——不强推。
- 物理路线这次与前三次的不同：带单位、不归一化（身体保住）；每个缸在每个工况实时解（不是一个代表气缸）；
  循环变动和流噪声是模型的一部分；有事件级的真值；管路是按拓扑建的网络而不是两个梳状滤波器。

车载构建只带座舱视角；赛道边/飞越、示波器是可选模块，只进桌面工作室。

## 7. 车载链路 v2

### 7.1 延迟预算：现在 vs v2

（"现在"一列是按代码算的估计；L0 的第一件事就是把它们**测**出来。）

| 环节 | 现在 | v2 |
|---|---|---|
| ECU 刷新 OBD 数值的节拍 | 未知（重复旧值说明存在） | 记录里直接量出来；估计器按实际采样时刻用 |
| 蓝牙一问一答 | 往返 60–140 ms → 读数到手时已旧 30–70 ms | 同样，但只是**修正**通道，不再是唯一信息 |
| 两次读数之间 | 约 100 ms，靠差分外推 | IMU 100 Hz 连续积分 |
| 主线程 50 Hz 定时器 | 0–20 ms 抖动 | 取消：音频回调直接向估计器要"出声时刻"的状态 |
| 合成器滑动 | 30 ms | 控制块 0.67 ms 内插 |
| 渲染队列 | 6 块 = 96 ms | 取消：在设备回调里直接渲染 |
| 硬件缓冲 | 约 10–20 ms | 约 5–10 ms |
| **音频路由**（`outputLatency`） | **没读**：扬声器约 10 ms；车机蓝牙 150–300 ms | 实时读取，作为估计器的预测步长；界面上显示 |
| **合计（未补偿）** | **约 250–300 ms（手机扬声器）；450–550 ms（车机蓝牙）** | 约 30–40 ms + 路由延迟，且全部进入预测 |

结论：**声音怎么到喇叭**决定了下限。车机蓝牙那 150–300 ms 是物理存在的，软件只能"预测到那么远的未来"去抵消，
预测越远越依赖模型。所以 v2 既要把自己造成的 200 ms 去掉，也要有一个真正的预测模型（7.5）。

### 7.2 传输与适配器

- 壳提供字节流（BLE / WiFi / 串口）；核心负责 ELM327 对话。
- **能力探测**：`ATI`/`STI` 识别芯片。STN 芯片（OBDLink 等）用它的快速模式；ELM327 克隆用"单帧、只等 1 条回复"的降级路径（这次踩出来的经验固化成一条已知路径）。
- 适配器怪癖（克隆失败后多发一条回复、对任何错误都说 UNABLE TO CONNECT……）进一张**适配器特性表**，不再散在代码里。

### 7.3 车辆档案 + 记住上次成功的

协议知识是数据。A3 8.5Y 的档案（来源：OBDb `Audi-A3` 2025/2026 实车记录 + 你车上 2026-10-21 的实测）：

```yaml
vehicle: audi-a3-8y-facelift          # 2025+ MQB Evo
obd:
  bus: can-29bit-500k                 # ELM: ATSP7
  request: 18DB33F1                   # 功能寻址
  engine_reply: 18DAF101              # 另有 02/03/04 模块同时应答
  service: 0x01
  legacy_11bit: silent                # 7DF / 7E0 / 22F40C 都不应答（2024 款及以前应答 7E0）
pids: [0x04 负荷, 0x0B 进气压力, 0x0C 转速, 0x0D 车速, 0x11 节气门,
       0x43 绝对负荷, 0x49/0x4A 踏板, 0x33 大气压, 0x5C 机油温度]   # 没有挡位 PID(0xA4)
engine: {idle: 760, redline: 6500}
```

- 连接成功后把"哪种适配器 + 哪条协议路径 + 哪些 PID"存下来；下次**直接走那条路**，目标 ≤ 2 s。21 级梯子降为"第一次遇到陌生车"才用的后备，且每一级来自档案库而不是硬编码。
- 档案库可以直接吃 OBDb 的公开数据（几百个车型），以后换车/给别人用不需要再试错。

### 7.4 调度

- 转速每次轮询必有；踏板隔次；车速、进气压力、绝对负荷轮转（每次请求仍然只有一个 CAN 帧）。
- 每条回复带**发送时刻和到达时刻**（单调时钟，不是墙上时钟），并标记"重复旧值"。
- 轮询节奏自适应：按测得的往返时间背靠背发，不固定间隔。

### 7.5 车辆状态估计器（核心改动）

**状态**：车速 v（连续——换挡时不跳）、离散挡位 g、加速度计零偏 b；以及离合分离时的自由转速。

**关系**：在挡时 `转速 = k_g × v`（k_g = 每挡的"每 km/h 多少转"，自动学习——现有 `GearLearner` 的结果搬进来）。

**信息来源，各司其职**：

| 来源 | 速率/延迟 | 用途 |
|---|---|---|
| 手机加速度计（CoreMotion，去重力后的纵向分量） | 100 Hz / 约 10 ms | **快通道**：积分得到 v 的变化；预测"出声时刻"的 v |
| OBD 转速 | 约 10 Hz / 旧 30–70 ms | 在挡时 `v = 转速/k_g` 是**很准的车速**，用来修正积分漂移和加速度计零偏；与当前挡不符 → 换挡/离合事件 |
| OBD 车速 | 约 2–3 Hz，1 km/h 分辨率 | 粗校验；起步/离合分离时用 |
| 踏板、绝对负荷、进气压力 | 约 3–5 Hz | 驱动合成器的负荷和涡轮；猛踩时的转速预测（踏板领先扭矩 100–300 ms） |
| GPS 车速 | 1 Hz | 长期真值，交叉校验 k_g |

**卫生**（现在都没有，F11）：每条测量先过离群值门限再用；数据过期（> 0.5 s 没有新读数）时估计器平滑地退到怠速而不是继续外推；
换挡检测用测量自己的时间戳，不用界面的步长。

**延迟的处理**：估计器保留最近 1 秒的状态历史。一条"30–70 ms 前采的"OBD 读数到达时，和**那个时刻**的历史状态比较，
把差值修正到现在——而不是把旧读数当成现在。

**输出**：音频回调查询 `t = 现在 + 输出延迟`；在挡时 `转速(t) = k_g × (v + a·Δt)`。

**模式**：

- *在挡*：如上。
- *离合分离 / 起步 / 停车 / 空挡*（转速与任何挡都对不上，或车速≈0）：退回"OBD 转速 + 踏板模型"（就是现在的做法，作为一个模式保留）。
- *换挡*：第一条"与当前挡对不上"的读数到达时，立即给出新挡目标 `k_{g±1} × v`（v 是连续的、已知的），用 DCT 的过渡曲线渲染，不等后面几条读数慢慢追。更早的触发（换挡瞬间的纵向冲击）等有了实测行程再评估。
- *发动机停机*（启停、滑行熄火，转速 = 0 而车在走）：模拟发动机不熄火——停车时怠速，滑行时按最后挡位挂着（可设置）。

**加速度计的前提与退化**：手机要相对车身固定（支架、杯架、中控凹槽都行；拿在手里不行）。车的前进方向在手机坐标系里的
指向由"加速度 ↔ OBD 车速变化"的相关自动标定，并持续给出置信度；置信度低（手机在动）时自动退回纯 OBD 模式，不会更糟，只是回到现在的水平。

**桌面仿真**（`_claude_scratch/rpmsim/twin2.py`；模拟的 A3 + 7 挡 DCT 跑 90 s：起步、经济换挡、巡航、猛踩、滑行、刹停、全油门；
OBD 往返 60–140 ms、ECU 50 ms 刷新；加速度计含噪声、漂移零偏和振动。**这些是假设，不是你车上的实测**，L0 录到真实行程后重跑）：

| 音频路径 | 做法 | 在挡：转速误差 | 在挡：抖动 | 在挡：残余延迟 |
|---|---|---|---|---|
| 有线/手机扬声器（约 60 ms） | 现在（OBD 差分外推） | 87 rpm | 20 rpm | 约 117 ms |
| | 估计器，不用加速度计 | 75 rpm | 17 rpm | 约 107 ms |
| | **估计器 + 加速度计** | **47 rpm** | **11 rpm** | **约 57 ms** |
| 车机蓝牙（约 220 ms） | 现在 | 180 rpm | 51 rpm | 约 247 ms |
| | 估计器，不用加速度计 | 148 rpm | 46 rpm | 约 188 ms |
| | **估计器 + 加速度计** | **98 rpm** | **40 rpm** | **约 70 ms** |

原型**还没解决**的两段（上面"模式"里的设计就是针对它们，尚未验证）：换挡窗口（三种做法误差都在 450–650 rpm，
瓶颈是"多久发现换挡了"）和起步/停车（原型里比现在差，实现时这一段直接沿用现在的做法）。

### 7.6 转速映射：虚拟传动

你的车日常在 1200–2500 rpm；大多数被模拟的发动机在那个转速并不好听。两种模式，都是数据驱动：

- **同步（默认）**：模拟转速是真实转速的单调函数，换挡点与真车完全重合（体感一致）。函数形状由三个锚点决定：
  怠速→怠速、你的**日常转速带**→这台模拟车的**好听转速带**、红线→红线。"好听转速带"是每台车 pack 里的一对数（由物理给初值：
  点火基频落在喇叭能重放且不发闷的范围；由你的耳朵改）。`direct / ratio / stretch / low-rev lift` 都是这个函数的特例，合并成它。
- **虚拟变速箱（可选）**：模拟发动机有自己的齿比和换挡逻辑，转速由**车速**决定——像另一台车在跑同一条路。更戏剧化，但换挡点不跟真车重合。

### 7.7 记录、回放、仿真车

- **行程记录器**（始终开着的环形缓冲，可导出文件）：适配器收发的原始字节 + 时间戳、IMU、GPS、音频状态（输出延迟、欠载）、估计器输出。
  一次行程约几 MB，用系统分享（隔空投送/文件 App）导出，不再是往聊天里贴日志。
- **回放**：同一份核心在桌面上吃记录文件，逐字节重演；改了估计器/调度后**重放你那次真实行程**，自动出分（出声时刻的转速误差、抖动、延迟）。
- **仿真 A3**：ELM327/STN 仿真器 + 车辆模型，带这台车的真实行为（只应答 29 位、四个模块同时回、重复旧值、往返抖动、
  克隆适配器的怪癖、启停、DCT 换挡）。进自动测试：10 月那几轮夜间试错里的每一个现象，都应该是一条能在桌面上跑红的测试。
- 结果：**每个里程碑上车一次**，带一张检查清单；其余在桌面完成。

### 7.8 只读

`link` 里**不存在**发送写入类服务的代码路径（清码 0x04、会话 0x10、安全访问 0x27、写 0x2E、例程 0x31、复位 0x11）。
允许发出的请求是一张白名单（AT 命令、0x01、0x09、只读 0x22），由一个测试枚举断言。

## 13. 不做什么 / 风险

- **不**用神经网络生成波形；**不**在录音上训练黑盒（沿用 surrogate 计划的边界）。
- **不**动已批准的旧声音：旧链冻结；一台车的新声音经你批准才替换它（§6.9）。
- **不**向车写任何东西。
- 风险：加速度计方案依赖手机固定——有自动退化，最坏回到现在的水平。
- 风险：换挡检测的延迟下限由 OBD 轮询速率决定（克隆适配器约 10 次/秒）。如果实测行程显示这是瓶颈，再考虑换 STN 芯片的适配器（OBDLink CX 一类，轮询速率高数倍）——**先看数据，不先买**。
- 风险：车机蓝牙的 150–300 ms 只能靠预测抵消，猛踩/换挡时预测必然有误差。如果你现在走的是车机蓝牙，最有效的单项改进可能是换一条有线的出声路径。
- 风险：新发声链不如旧声音好听——物理路线以前三次输给过耳朵（§6.1）。对策：单事件有实录真值、先在有真值的 A3 上证明、逐车 A/B、旧声音并存到被你批准替换为止（§6.9）。
- 风险：每台车需要排气拓扑数据（管长、管径、汇合、消声器结构），现有预设只有几个标量。对策：check set 先手工查证；其余车按家族给默认拓扑，再逐步细化。
